## 🛠️ Topic 1: Django Architecture & Database Design

### Q1: Describe the overall architecture of this Gym Application.
**Answer:**
* **Framework:** The application is built using the **Django** Python web framework, which follows the Model-View-Template (MVT) design pattern.
* **Separation of Concerns:** 
  * **Models (`models.py`):** Define the database schemas, field rules, and relationships (e.g., `Workout`, `MemberModels`, `UserProfile`, `GeneratedPlan`).
  * **Views (`views.py`):** Handle request routing, authentication checks, form processing, and return either HTML templates or JSON data for frontend fetch requests.
  * **Services Layer (`services/`):** Houses business logic for external integrations, keeping the views cleaner. `GeminiService` handles Groq LLM logic, and `YouTubeService` interacts with the YouTube search/video validation endpoints.
  * **Templates (`templates/`):** Contains HTML markups styled with a custom dark-neon Tailwind CSS design.

### Q2: What is the database design for persisting AI-generated fitness plans?
**Answer:**
We employ a hybrid approach:
* **Relational Profile:** A user's physical metrics (weight, height, age, goal, experience level, workout location) are stored as structured columns in the `UserProfile` table.
* **Dynamic plan data:** The generated plan output contains highly structured nested lists and maps (e.g., workout exercises, repetitions, sets, daily calorie counts, specific meals). Rather than creating a highly complex relational schema with dozens of table joints, the plan is serialized as a JSON string and persisted in the `plan_data` `TextField` of the `GeneratedPlan` model.
This balance provides flexibility to query user metrics while easily storing variable-length JSON structures generated by Third-Party LLM APIs.

### Q3: Why is `plan_exists` checked in the `home` and `register_member` view, and how does it affect the user journey?
**Answer:**
* **Logic:** When an authenticated user requests the homepage or the pricing/signup page, the view queries:
  ```python
  plan_exists = GeneratedPlan.objects.filter(user=request.user).exists()
  ```
* **UX Impact:** In the templates (e.g., `register_member.html`), the pricing block for the Free Core plan checks `plan_exists`. If true, instead of displaying the registration flow or price, it renders: `"You have accessed this plan"` with a direct navigation link `"Go to your plan"`. This state persistence prevents users from repeating the questionnaire unnecessarily and enhances navigation convenience.

## 🤖 Topic 2: LLM & External API Integration (Groq & YouTube)

### Q4: How does the application generate AI fitness plans, and how do you handle LLM response parsing and failure?
**Answer:**
* **LLM Client:** Managed through `GeminiService` (kept named for backwards-compatibility) using the `Groq` python package.
* **Models Utilized:** A priority list `GROQ_MODELS = ["llama-3.3-70b-versatile", "llama-3.1-8b-instant", "mixtral-8x7b-32768"]` allows the system to try the most capable model first and dynamically fallback to others on failure.
* **Sanitization/Parsing:** The system sets strict API system-prompts enforcing JSON output: `"You ONLY respond with valid JSON. No markdown, no explanation, no code blocks."`
  In python, the code strips any accidental Markdown code blocks:
  ```python
  if raw_text.startswith("```"):
      raw_text = raw_text.split("```")[1]
      if raw_text.startswith("json"):
          raw_text = raw_text[4:]
  ```
  It then parses it via `json.loads`.
* **API Redundancy/Fallback:** Under `Groq` rate limits (HTTP 429) or JSON corruption errors, the service catches the exception and falls back to a clean mock diet/workout generator to ensure the user gets a functional interface.

### Q5: How is diet plan customization tailored to user goals (e.g. bulking vs cutting) while adhering to regional accessibility?
**Answer:**
In `GeminiService._build_prompt`, we evaluate the user goal:
* **Fat Loss:** Instruction directs the model to prescribe low-carb, high-protein Indian items (paneer, eggs, sprouts, dal, curd) with calorie targets between 1400-1800 kcal.
* **Weight Gain:** Instruction directs a high-calorie surplus (2700-3400 kcal) using calorie-dense local foods (peanut butter, bananas, whole eggs, oats, milk, rajma, ghee).
* **Cost/Ingredient Restriction:** The prompt explicitly instructs: *"Do NOT suggest fancy or expensive ingredients like salmon, avocado, quinoa, berries, asparagus, or chia seeds."* This forces the LLM to deliver practical, local, and budget-friendly meals.
* **Exact Time Bracket:** The prompt enforces adding target meal consumption timing in 24-hr `[HH:MM:SS]` formatting at the text endings.

### Q6: How does the application query and validate workout demonstration videos?
**Answer:**
Managed by `YouTubeService` using a 2-stage verification workflow:
1. **Search Request:** Calls Google's YouTube `search` API querying `{exercise_name} workout tutorial` to retrieve the top 5 video IDs.
2. **Quality/Availability Check:** Before showing the video, we run a query to the YouTube `videos` endpoint (`videos.list`) requesting details for all retrieved video IDs:
   - We verify `privacyStatus == "public"`.
   - We verify `embeddable == True` (to reject videos where authors disabled external embedded iframe playback).
   - We parse the ISO 8601 duration format (e.g., `PT1H2M10S` to `1 hr 2 mins 10 secs`).
3. **Local Failbacks:** If keys are missing or API calls fail, the service returns verified, pre-screened video IDs from a local python lookup dictionary containing common exercises (like Push-Ups: `IODxDxX7oi4`, Downward Dog: `UsTTTYbBdQg`).

## 🔒 Topic 3: Forms, Authentication & Backend Security

### Q7: What is the purpose of `@csrf_exempt` in `api_generate_plan` and `save_profile` views, and what are their security implications?
**Answer:**
* **Purpose:** `@csrf_exempt` tells Django to bypass Cross-Site Request Forgery (CSRF) token checks for POST requests hitting these specific AJAX endpoints. This simplifies JavaScript fetching since the frontend doesn't need to read and send the CSRF cookie token header.
* **Implications:** By disabling CSRF protection, the application becomes vulnerable to CSRF attacks if authentication relies on session cookies. If a user visits a malicious website while logged into their gym dashboard, the malicious site could make background POST requests to `/api/generate_plan/` or `/save_profile/` using the user's active session.
* **Remediation:** Remove `@csrf_exempt` and configure the JavaScript browser client to extract the cookie token:
  ```javascript
  const csrfToken = document.cookie.split('; ').find(row => row.startsWith('csrftoken=')).split('=')[1];
  ...
  headers: {
      'Content-Type': 'application/json',
      'X-CSRFToken': csrfToken
  }
  ```

### Q8: How does user signup view implement special security checks for admin emails?
**Answer:**
In `signup_view`, after validating form constraints, the system checks if the newly registered email address matches an existing admin/superuser:
```python
if User.objects.filter(email=email, is_superuser=True).exists():
    messages.error(request, "This email is reserved and cannot be used.")
    return render(...)
```
This protects administration accounts and credentials by blocking unauthorized registration using reserved domain names or administration-associated email profiles.

## 🧪 Topic 4: Testing & Quality Assurance

### Q9: How are mock objects and unit tests organized to verify recommendation models off-grid (without internet connectivity)?
**Answer:**
In `gymapp/tests.py`:
* **Environment Overrides:** We use `@override_settings(GROQ_API_KEY="", YOUTUBE_API_KEY="")` directly over test methods. This forces the views and service layers to trigger local fallback mock paths, letting us test program logic offline without calling third-party services.
* **API Mocking:** We use standard `unittest.mock.patch("requests.get")` to mock API responses. By simulating HTTP calls returning fake JSON payloads (containing both embeddable and non-embeddable video metadata), we can test that the `YouTubeService` correctly filters out non-embeddable videos and picks the embeddable ones, without making actual network requests.

## 🎨 Topic 5: Frontend Layout & Integration

### Q10: How does the front-end handle dynamic form submissions and page updates?
**Answer:**
Instead of standard HTML page transitions on submits, the application uses **AJAX requests** via the JavaScript `fetch` API:
1. Profile details are submitted asynchronously to the JSON endpoints in the backend.
2. The views save database model instances and return JSON status objects.
3. The JavaScript frontend routes the browser to subsequent pages (e.g., `choose_workout`) based on success responses, maintaining smooth single-page flow visuals.
4. CSS styling is built using utility-first classes powered by custom configured Tailwind CSS variables (`tailwind.config.js`).
